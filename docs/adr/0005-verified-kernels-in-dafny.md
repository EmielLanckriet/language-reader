# ADR-0005: Verified Kernels In Dafny

**Status**: Accepted
**Date**: 2026-08-28
**Relates to**: Constitution Principles II and VII, Additional Constraints (v1.3.0);
ADR-0002; ADR-0004

## Context

ADR-0002 made word identity revisable by attaching status to a surrogate lexeme id, so that
refining identity is a merge or split of lexemes rather than a rewrite of the status table. That
argument has a load-bearing premise: **merge and split must actually be correct.** If they are
subtly wrong, identity is not revisable, ADR-0002's central claim is false, and the failure
surfaces only after months of accumulated earned data.

Two things then changed the weight of that premise.

First, Principle II's mandatory test-first list did not include merge and split. The one operation
whose failure invalidates an ADR was outside the project's only rigour requirement.

Second, merge and split turned out not to be back-office machinery at all. Chinese segmentation is
unavoidably imperfect — word-hood is undefined, so a segmenter can disagree with a learner without
being wrong — and the developer's concrete complaint about LingQ is exactly this. The fix is
letting the user correct segmentation, and correcting segmentation *is* merging and splitting
adjacent tokens. These operations are therefore a slice-1 user-facing feature, invoked frequently,
against real data.

The operations are also algebraic. Merging three lexemes must not depend on order; status
resolution must be deterministic; no token may be orphaned; split must recover something
equivalent to what merge consumed. Properties of this shape are sampled by property-based testing
and *proved* by a verifier, and their failure mode — a rare ordering on rare data, discovered late
— is precisely the kind testing is worst at catching.

The developer works in formal verification and has asked to experience agentic development in
Dafny. That is a stated goal of the project in its own right, independent of the technical
argument, but it does not have to be traded against it: the strongest technical candidate for
verification and the desired learning exercise are the same piece of code.

## Decision

**Dafny is added to the technology stack, scoped to verified domain kernels.**

**In scope.** Small, pure, algebraic components of the domain core:

- Lexeme merge and split, including status resolution — slice 2.
- Status event replay: that folding the `status_event` log reproduces current status.
- Offset anchoring across re-segmentation: that retained character offsets stay valid when the
  token stream is recomputed — a candidate, not yet committed.

**Out of scope.** Anything touching I/O, storage, the network, analysis libraries, or the UI.
Kernels take values and return values. If a component needs a library, it is not a kernel. This
scope is what made the decision survive ADR-0007's removal of the entire backend without
alteration.

**Dafny is the source; generated Python is an artifact.** Per the carve-out in ADR-0004, the
generated Python is never read and never hand-edited. It is regenerated by a committed build
command, sits behind a hand-written Python interface, and is judged by whether the Dafny is
readable — as compiler output is judged by its source. Principle VII applies in full to the
`.dfy` files.

**Proved properties do not get duplicate example-based tests.** A property proved in Dafny is not
re-tested in pytest. What *is* tested in Python is the adapter layer: that domain values are
correctly marshalled into and out of the kernel. That boundary is unverified and is where errors
will actually live.

**Escape hatch.** If Dafny proves a net drag, the kernel is replaced by hand-written Python behind
the same interface, tested with `hypothesis` against the same properties. The blast radius is one
module by construction. This is a foreseen outcome, not a failure.

## Toolchain (verified working, 2026-08-28)

- **Dafny 4.11.0.**
- `dotnet tool install -g dafny` **FAILS** on this machine: Dafny 4.11.0 targets `net8.0` and the
  installed SDK is .NET 6.0.132. Recorded so it is not rediscovered.
- The self-contained release is used instead: `dafny-4.11.0-x64-ubuntu-22.04.zip`, unpacked to
  `~/.local/opt/dafny`. It bundles its own runtime and does not use the system .NET. It is NOT on
  `PATH`; invoke it by full path or add it deliberately.
- **Planned before slice 2**: install .NET 8 and move to `dotnet tool install -g dafny`. The
  self-contained build is a stopgap that no package manager tracks and that must be upgraded by
  hand. Dafny is not used until slice 2, so there is time to do this properly rather than under
  deadline.
- Confirmed end to end for **Python**: `dafny verify` proves the lemmas; `dafny build -t:py` emits
  a Python package; the result imports and runs from ordinary Python. Datatype constructors
  surface as `Status_Known()`, top-level functions as `module_.default__.FunctionName`.
- **Superseded by ADR-0007: the target is now `js`, also confirmed working.** `dafny build -t:js`
  verifies the same lemmas, emits `Status.js`, and runs under Node. It requires `bignumber.js` as
  an npm dependency, because Dafny integers are arbitrary-precision; without it the build fails at
  the run step with `Cannot find module 'bignumber.js'`, which looks like a Dafny failure and is
  not.
- The hand-written adapter exists to hide the generated shapes, whichever target is used.

## Alternatives Rejected

**Test merge/split with `hypothesis` only.** Rejected as the primary mechanism, though retained as
the fallback. Property-based testing samples a space; it does not establish absence. For an
operation whose failure invalidates an architectural decision and corrupts irreplaceable earned
data, sampling is the weaker guarantee. Note this was rejected on strength, not on effort —
`hypothesis` would have been less work.

**Dafny as specification only: model and prove in Dafny, hand-write the Python, test the Python
against the same properties.** Rejected. The refinement from Dafny to Python would be unchecked
and would live only in the developer's head, which forfeits most of the guarantee while keeping
all of the modelling cost. Also the weaker learning exercise: writing Dafny that is then discarded
is not the experience being sought.

**Verify more of the system.** Rejected. Kernels are viable precisely because they are pure and
small. Extending Dafny to anything touching I/O or libraries would import large amounts of
friction for components whose bugs are cheap and discoverable.

**Rust or a similar language for the kernel instead.** Rejected: it would add a compiled-language
toolchain and FFI without providing proof, which is the entire reason for the exercise.

## Consequences

**Easier.** ADR-0002's central claim becomes proved rather than asserted. The user-facing
segmentation-correction feature rests on verified operations. The developer gets the requested
Dafny experience on code that genuinely warrants it rather than on a contrived example.

**Harder.** A second toolchain, a build step, and a self-contained Dafny installation that is not
managed by any package manager and must be upgraded by hand. Contributors — and future sessions —
must know that editing the generated Python is meaningless. Verification time is added to the
build.

**On the .NET situation.** The self-contained binary avoids the SDK version problem entirely, but
it also means Dafny will not track system updates. Installing .NET 8 and switching to
`dotnet tool install` is planned before slice 2, when Dafny is first actually used.

**Revisit if.** Verification of merge/split turns out to require modelling so much of the
surrounding data structure that the kernel stops being small — that would mean the operations are
not as self-contained as assumed, and the `hypothesis` fallback becomes correct. Alternatively,
if the adapter layer accumulates enough logic to become the real source of bugs, the boundary is
in the wrong place.
